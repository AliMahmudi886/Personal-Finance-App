# Master audit report

**Repository** [AliMahmudi886/Personal-Finance-App](https://github.com/AliMahmudi886/Personal-Finance-App)
**Scope** Public `main` at `66f4cb5`, compared with the unstaged primary checkout where relevant. Fixes target `audit/continuous-engineering`.
**Runtime** Windows, Python 3.12, Flask, Jinja, SQLite, pandas, scikit-learn, TensorFlow and TextBlob.

## Summary

The active WSGI path is `app:app`. Server-rendered forms call the SQLite layer in `models.py`, and analytics query the same ledger by account. The main branch contained a populated database in its public Git tree, a fixed session signing key, broken expense submission, and no declared runtime dependencies. The maintenance branch addresses those current-tree and runtime defects. Public history containment and exact monetary persistence remain release blockers.

This review covered the tracked Python and Jinja sources, manifests, configuration, static references, schema and deployment entry points. Existing binary ledgers were inspected read-only for schema and record presence. Verification ran on disposable databases. The primary checkout has independent, uncommitted changes, including experimentation with a shared spreadsheet under the static directory. That spreadsheet and those changes were excluded from the branch. Its contents were outside the audit scope.

## Verification and performance

The route suite covers registration, local signin, logout, account isolation, uploads, inputs, SQLite compatibility and analytics. It includes real TensorFlow runs on synthetic records. A Waitress server answered real HTTP requests against a temporary database. Edge rendered the active views, including forecast and autoencoder endpoints. Thirteen authenticated routes were checked at 390, 768 and 1,440 px with no full-page horizontal overflow in the fixtures. No JavaScript exceptions or failed resource requests were observed in that run.

One local measurement on Windows found approximately 1.96 s for cold WSGI application import and schema initialization, a 1.0 ms median across 19 warmed loopback requests to `/login`, and 4.59 s to first render the forecast with TensorFlow. These figures are sample-specific. Load, concurrency, production proxy performance, and a comparable before-and-after benchmark remain open.

Tests and lint are scoped to the active web runtime. The full-repository legacy lint inventory is tracked in PF-014. No application package or frontend bundle is configured. Verification for this Flask runtime consists of installing from pins, compiling Python and starting the WSGI process. Dependency audit scope is the pinned Python runtime. CDN assets and a production container were outside this scan.

## Roadmap and approval

1. Contain the public data incident. Have the owner verify backups, identify affected records and copies, decide on repository visibility and history, and approve any coordinated action. Visibility changes can affect collaborators and automation. Git history rewrites require coordination and recovery references.
2. Reconcile a private backup and approve currency, rounding and exact-decimal storage. Validate per-account values before and after migration. Keep the old snapshot available for rollback.
3. Verify staging deployment, TLS and proxy behavior, login throttling and credential rotation. Approve any production authentication change or release. Re-enable Google only after reviewed local account linking.
4. Validate backup recovery, concurrency, pagination and query plans. Decide on missing core finance operations before introducing new behavior.
5. Backtest analytics, bound training cost and finish keyboard, screen-reader and asset-supply review.
